# 10. Input-to-output latency measurements

Research question: how deterministic can this hardware be as a PLC / I/O module, and what does
each software layer cost? The same measurement is repeated for every software variant; only the
software changes.

## Setup

```
P9.29 (ehrpwm0B, hardware PWM) ──┬──▶ logic analyzer channel 0   (stimulus)
                                 └──▶ P8.39 (I0)
software under test copies I0 → Q0
P8.43 (Q0) ──────────────────────────▶ logic analyzer channel 1   (response)
GND (P9.1) ──────────────────────────▶ logic analyzer GND
```

- Bare board (no carrier), pinmux profile `default` (Q0..Q3 on P8.43..46, I0..I3 on P8.39..42,
  ehrpwm0B on P9.29).
- The stimulus is generated by the eHRPWM module, so it does not depend on the software under
  test. Enable it over SSH (`/sys/class/pwm/pwmchip0`, channel 1 = ehrpwm0B):
  ```sh
  C=/sys/class/pwm/pwmchip0; [ -d $C/pwm1 ] || echo 1 > $C/export
  echo 93685000 > $C/pwm1/duty_cycle; echo 187370000 > $C/pwm1/period
  echo 93685000 > $C/pwm1/duty_cycle; echo 1 > $C/pwm1/enable
  ```
  **The stimulus period must not be a multiple of the software cycle time.** 200 ms against a
  50 ms PLC cycle samples the input at the same phase every time and gives a narrow, meaningless
  distribution (first attempt: 3.3 ms ± 0.1 ms). 187.37 ms is not commensurate with 50 ms, 10 ms
  or 1 ms cycles and sweeps all phases.
- Logic analyzer: Kingst LA2016, two channels, 3.3 V threshold. Sample rate ≥ 20× finer than the
  smallest latency of interest (20 kHz for a 50 ms cycle, ≥ 1 MHz for 1 ms cycles, 10–100 MHz for
  bare metal). Capture ≥ 100 s (≈ 1000 edges). Export CSV (KingstVIS: `Time[s], Channel 0, Channel 1`,
  one row per change).
- Analysis: `python firmware/tools/latency.py capture.csv` pairs every stimulus edge with the
  next response edge and prints min / median / mean / p99 / p99.9 / max, jitter, stdev and a
  histogram. Raw captures are kept in `docs/latency/`.

Reading variant 1: the distribution is flat from 1.9 to 51.8 ms, i.e. uniform over one 50 ms
cycle (the edge arrives at a random phase of the cycle) plus a fixed ~1.9 ms for the cycle's own
work (reading inputs and the 8 ADC channels through sysfs, the program, writing outputs). The
cycle-to-cycle jitter of plain Linux is visible in the phase-locked first attempt: stdev 59 µs,
spread 220 µs over 100 cycles.

Reading variant 2: again uniform, but 1.3 ms wide starting at 1.28 ms: one OpenPLC cycle takes
~1.3 ms of work on this CPU, so a 1 ms task interval just runs back to back (load average 2.8).
The fixed part is the cycle work itself; the PLC runtime, not the kernel, sets the floor here.

Reading variant 3: the Linux floor through libgpiod is ~2.7 µs (one GET_VALUES and one
SET_VALUES ioctl) plus the poll loop period (~4.5 µs, uniform); no outlier above 10 µs in 50 s
even on a non-RT kernel, with the system otherwise idle. Costs the whole CPU (the RT throttle
leaves 5% for everything else).

Reading variant 4: uniform over exactly one 1 ms period on top of ~15 µs (timer wake-up from
idle plus the two ioctls); no wake-up later than the period in 50 s. CPU almost idle. Compare
with variant 2: the same 1 ms cycle costs 1.3 ms in OpenPLC and 15 µs here.

Reading variant 5: a sharp peak at 122-130 us with a tail to 284 us. The ~120 us floor is far
above the ioctl cost seen in variant 3, so it is the wake-up path itself: GPIO interrupt, exit
from the CPU idle state, gpiolib event, wake of the user thread, then the two ioctls. Variant 5b
repeats it with the deeper cpuidle states disabled to separate idle-exit from the rest.

Reading variant 5b: disabling the deep idle state did not lower the floor (median 144 vs
128 us), so the ~120 us is not idle exit. Candidates: the cpufreq `ondemand` governor (CPU at
300 MHz when idle), the threaded GPIO IRQ path of gpiolib-cdev, GPIO bank runtime PM.
`latency-echo -e` now prints the time from the edge's kernel timestamp (taken in the hard IRQ)
to the thread running again, which splits the path in two.

Reading variant 5c: the `ondemand` governor was the ~100 us: with the system idle the CPU sits
at 300 MHz and the whole wake-up path runs 3x slower, plus the frequency ramp. With a fixed
1 GHz the edge-to-output latency is 41-72 us. `latency-echo` itself reports edge timestamp
(hard IRQ) to thread running: min 27, mean 34, max 139 us over 2085 events. So of the ~49 us
median about 34 us are the gpiolib threaded-IRQ path and the scheduler (two wake-ups on a
kernel without preemption), ~2 us the two ioctls, and ~13 us input synchronisation and IRQ entry.
A fleet image should therefore ship `performance` (or a fixed OPP) and keep `mpu_gate`;
the next lever is kernel preemption.

Reading variant 6: identical to 5c (IRQ to thread mean 34.5 vs 34.3 us). On an idle system
there is nothing to preempt; the ~34 us are the intrinsic cost of the gpiolib threaded IRQ path
(hard IRQ -> IRQ thread -> kfifo -> poll wake-up -> user thread) at 1 GHz. Preemption models
can only show a difference under load, which is what the next variants measure.

Reading variant 6L: under load the median is 3.5x the idle value and the tail reaches 1.45 ms;
`latency-echo` shows all of it in IRQ -> thread (min 95, mean 177, max 1451 us). The hard IRQ
still fires on time; the gpiolib IRQ thread (SCHED_FIFO 50 by default) and the network softirqs
compete with the user thread for the single core. Levers to test: raise the IRQ thread's
priority above the user thread, PREEMPT_RT (softirqs become preemptible threads), or avoid the
threaded path with a tiny in-kernel handler.

Reading 5cL vs 6L: the same within noise (median 178 vs 173 us, max 1.41 vs 1.45 ms).
CONFIG_PREEMPT buys nothing on this board, idle or loaded: the tail is work that full
preemption does not interrupt either (softirqs for the 3000 pkt/s network RX, and the NAND
driver, which polls the chip's ready/busy in the kernel during writes). The next captures
isolate the two: load without NAND writes, and load with NAND writes only.

Planned variants: 5cL-net (hogs + network only), 5cL-nand (NAND writes only); the same on a PREEMPT_RT
kernel (needs the external 6.12-rt patches: 32-bit ARM has no ARCH_SUPPORTS_RT in 6.12); bare metal / RTOS on
the A8 loaded by U-Boot (no Linux). The AM3352 has no PRU (verified: the PRU-ICSS address space
gives a bus error and its PRCM module never leaves the disabled state), so a PRU variant is not
possible on this board.
