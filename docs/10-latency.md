# 10. Input-to-output latency measurements

Research question: how deterministic can this hardware be as a PLC / I/O module, and what does
each software layer cost? The same measurement is repeated for every software variant; only the
software changes.

## Setup

```
P9.29 (ehrpwm0B, hardware PWM) ──┬──▶ logic analyzer channel 0   (stimulus)
                                 └──▶ P8.39 (I0)
software under test copies I0 → Q0
P8.43 (Q0) ──────────────────────────▶ logic analyzer channel 1   (response)
GND (P9.1) ──────────────────────────▶ logic analyzer GND
```

- Bare board (no carrier), pinmux profile `default` (Q0..Q3 on P8.43..46, I0..I3 on P8.39..42,
  ehrpwm0B on P9.29).
- The stimulus is generated by the eHRPWM module, so it does not depend on the software under
  test. Enable it over SSH (`/sys/class/pwm/pwmchip0`, channel 1 = ehrpwm0B):
  ```sh
  C=/sys/class/pwm/pwmchip0; [ -d $C/pwm1 ] || echo 1 > $C/export
  echo 93685000 > $C/pwm1/duty_cycle; echo 187370000 > $C/pwm1/period
  echo 93685000 > $C/pwm1/duty_cycle; echo 1 > $C/pwm1/enable
  ```
  **The stimulus period must not be a multiple of the software cycle time.** 200 ms against a
  50 ms PLC cycle samples the input at the same phase every time and gives a narrow, meaningless
  distribution (first attempt: 3.3 ms ± 0.1 ms). 187.37 ms is not commensurate with 50 ms, 10 ms
  or 1 ms cycles and sweeps all phases.
- Logic analyzer: Kingst LA2016, two channels, 3.3 V threshold. Sample rate ≥ 20× finer than the
  smallest latency of interest (20 kHz for a 50 ms cycle, ≥ 1 MHz for 1 ms cycles, 10–100 MHz for
  bare metal). Capture ≥ 100 s (≈ 1000 edges). Export CSV (KingstVIS: `Time[s], Channel 0, Channel 1`,
  one row per change).
- Since 2026-11-03 the same LA2016 is driven from the PC with **sigrok** (`E:\tools\sigrok-cli`,
  `E:\tools\pulseview`; driver `kingst-la2016`, WinUSB via Zadig, firmware extracted from the
  Linux KingstVIS with `sigrok-fwextract-kingst-la2016` into `%LOCALAPPDATA%\sigrok-firmware`),
  so a capture is one command and needs nobody at the GUI:
  ```
  sigrok-cli -d kingst-la2016 -C CH0,CH1 -c samplerate=2m:voltage_threshold=1.4-1.4 --time 100000 -o capture.sr
  python firmware/tools/latency.py capture.sr
  ```
  CH0 = stimulus, CH1 = response, 1.4 V threshold (the LA2016 has no 3.3 V setting; 1.4 V is
  fine for 3.3 V logic). 2 MHz gives 0.5 µs resolution; 10 MHz for 100 s was unreliable over
  USB. `latency.py` reads the `.sr` directly. Do not export with `-O csv:dedup=true`: its time
  column is the row number.
- Analysis: `python firmware/tools/latency.py capture.csv` pairs every stimulus edge with the
  next response edge and prints min / median / mean / p99 / p99.9 / max, jitter, stdev and a
  histogram. Raw captures are kept in `docs/latency/`.

Reading variant 1: the distribution is flat from 1.9 to 51.8 ms, i.e. uniform over one 50 ms
cycle (the edge arrives at a random phase of the cycle) plus a fixed ~1.9 ms for the cycle's own
work (reading inputs and the 8 ADC channels through sysfs, the program, writing outputs). The
cycle-to-cycle jitter of plain Linux is visible in the phase-locked first attempt: stdev 59 µs,
spread 220 µs over 100 cycles.

Reading variant 2: again uniform, but 1.3 ms wide starting at 1.28 ms: one OpenPLC cycle takes
~1.3 ms of work on this CPU, so a 1 ms task interval just runs back to back (load average 2.8).
The fixed part is the cycle work itself; the PLC runtime, not the kernel, sets the floor here.

Reading variant 3: the Linux floor through libgpiod is ~2.7 µs (one GET_VALUES and one
SET_VALUES ioctl) plus the poll loop period (~4.5 µs, uniform); no outlier above 10 µs in 50 s
even on a non-RT kernel, with the system otherwise idle. Costs the whole CPU (the RT throttle
leaves 5% for everything else).

Reading variant 4: uniform over exactly one 1 ms period on top of ~15 µs (timer wake-up from
idle plus the two ioctls); no wake-up later than the period in 50 s. CPU almost idle. Compare
with variant 2: the same 1 ms cycle costs 1.3 ms in OpenPLC and 15 µs here.

Reading variant 5: a sharp peak at 122-130 us with a tail to 284 us. The ~120 us floor is far
above the ioctl cost seen in variant 3, so it is the wake-up path itself: GPIO interrupt, exit
from the CPU idle state, gpiolib event, wake of the user thread, then the two ioctls. Variant 5b
repeats it with the deeper cpuidle states disabled to separate idle-exit from the rest.

Reading variant 5b: disabling the deep idle state did not lower the floor (median 144 vs
128 us), so the ~120 us is not idle exit. Candidates: the cpufreq `ondemand` governor (CPU at
300 MHz when idle), the threaded GPIO IRQ path of gpiolib-cdev, GPIO bank runtime PM.
`latency-echo -e` now prints the time from the edge's kernel timestamp (taken in the hard IRQ)
to the thread running again, which splits the path in two.

Reading variant 5c: the `ondemand` governor was the ~100 us: with the system idle the CPU sits
at 300 MHz and the whole wake-up path runs 3x slower, plus the frequency ramp. With a fixed
1 GHz the edge-to-output latency is 41-72 us. `latency-echo` itself reports edge timestamp
(hard IRQ) to thread running: min 27, mean 34, max 139 us over 2085 events. So of the ~49 us
median about 34 us are the gpiolib threaded-IRQ path and the scheduler (two wake-ups on a
kernel without preemption), ~2 us the two ioctls, and ~13 us input synchronisation and IRQ entry.
A fleet image should therefore ship `performance` (or a fixed OPP) and keep `mpu_gate`;
the next lever is kernel preemption.

Reading variant 6: identical to 5c (IRQ to thread mean 34.5 vs 34.3 us). On an idle system
there is nothing to preempt; the ~34 us are the intrinsic cost of the gpiolib threaded IRQ path
(hard IRQ -> IRQ thread -> kfifo -> poll wake-up -> user thread) at 1 GHz. Preemption models
can only show a difference under load, which is what the next variants measure.

Reading variant 6L: under load the median is 3.5x the idle value and the tail reaches 1.45 ms;
`latency-echo` shows all of it in IRQ -> thread (min 95, mean 177, max 1451 us). The hard IRQ
still fires on time; the gpiolib IRQ thread (SCHED_FIFO 50 by default) and the network softirqs
compete with the user thread for the single core. Levers to test: raise the IRQ thread's
priority above the user thread, PREEMPT_RT (softirqs become preemptible threads), or avoid the
threaded path with a tiny in-kernel handler.

Reading 5cL vs 6L: the same within noise (median 178 vs 173 us, max 1.41 vs 1.45 ms).
CONFIG_PREEMPT buys nothing on this board, idle or loaded: the tail is work that full
preemption does not interrupt either (softirqs for the 3000 pkt/s network RX, and the NAND
driver, which polls the chip's ready/busy in the kernel during writes). The next captures
isolate the two: load without NAND writes, and load with NAND writes only.

Reading 5cL-net: without flash writes the median halves (178 -> 77 us) and the tail shrinks
from 1.41 to 0.82 ms. The network softirq at 3000 pkt/s alone still produces a sub-millisecond
tail; the NAND write path adds the rest.

Reading 5cL-nand: flash writes do not produce rare long spikes like the network does; they
raise the whole floor by ~130 us (compact distribution shifted from 49 to 213 us median). The
NAND driver keeps the CPU in non-preemptible sections of about that length while a write is
in progress, and UBIFS/dd keep writes going continuously.

## PREEMPT_RT (2026-11-03)

Mainline 6.12 has no `ARCH_SUPPORTS_RT` for 32-bit ARM, so `CONFIG_PREEMPT_RT` cannot be
selected from the plain tree. The external patch `patch-6.12.111-rt21` (53 files, 2268 lines)
adds it and applies cleanly on 6.12.112. For these measurements `build-kernel.sh` kept a second
worktree (`~/antminer/linux-rt`) with the patch applied, built the same `kernel/defconfig` with
only the preemption model changed (`PREEMPT_RT=y`), and wrote `firmware/out/uImage-rt.bin`
(2.77 MiB, fits the NAND kernel partition). The kernel was netbooted with the normal initramfs
and the overlay from NAND: boots in the same time, all services start, threaded IRQs
(`irq/NN-...` kernel threads) are visible in `ps`.

Measured first without wiring: the timer wake-up latency of a SCHED_FIFO 80 thread with a
1 ms period (the "cycle jitter" a PLC runtime would see), with `latency-timer.c` and
`cyclictest` side by side, 60 000 wake-ups per run, `performance` governor, OpenPLC stopped.
Load = `latency-load.sh start cpu nand net` + `latency-flood.py` at 3000 pkt/s. Raw output:
`docs/latency/2026-11-03-timer-rt-vs-plain.txt`.

Reading: the two tools agree within a few µs, so `latency-timer.c` can be used where the feed
is not reachable. On the plain kernel even an idle system has a tail to ~380 µs (p99.9 267 µs):
the periodic housekeeping of the kernel (timers, RCU, the network stack for the few packets of
SSH/DHCP, NAND background work) runs in non-preemptible context and delays the wake-up. Under
load the plain kernel's p99 is 200 µs and the max ~350 µs, the same order as the 1.4 ms tail of
the interrupt echo in 5cL/6L (that one also contains the gpiolib IRQ thread, which the timer
path does not). PREEMPT_RT removes the tail: idle max 53 µs with p99.9 at 23 µs, and under the
full load max 82 µs with p99 58 µs, i.e. the loaded RT kernel has a smaller tail than the idle
plain kernel. The mean under load (35 µs) is the cost of sharing one core with the hogs and the
threaded softirqs; the floor (13 µs idle) is unchanged, it is the timer IRQ + wake-up itself.
The NAND writes that cost +130 µs per event on the plain kernel (5cL-nand) no longer show as
a floor shift: the NAND driver's polling now runs in a preemptible IRQ thread below
SCHED_FIFO 80.

### The I0 -> Q0 interrupt echo on PREEMPT_RT (same day, same wiring, sigrok captures)

Variants 5c (idle) and 6L (cpu + nand + 3000 pkt/s) repeated on both kernels within one hour,
`latency-echo -e`, SCHED_FIFO 80, `performance`, 100 s at 2 MHz, 1068 edges each. The plain
kernel was measured again the same way so that the comparison does not depend on the October
captures (which were taken with KingstVIS at 200 kHz). Raw data: `docs/latency/2026-11-03-*.sr`
with the `latency.py` report next to each as `.txt`.

Reading: on the interrupt path PREEMPT_RT costs ~17 µs on the median of an idle system (59.5
vs 42.5 µs): the hard IRQ now only wakes the gpiolib IRQ thread, which wakes the user thread,
i.e. one more full context switch, and every spinlock on the way is a sleeping lock. Under load
the RT kernel's median is lower (187 vs 203 µs), its p99 lower (305 vs 347 µs) and its maximum
lower (330 vs 422 µs), but the gain is much smaller than on the timer path (table above: 82 vs
351 µs max), and both kernels have the same ~150-165 µs floor under load. So the tail of the
echo under load is not non-preemptible kernel work any more (RT removed that, as the timer test
shows); what remains is the wake-up chain itself competing for one core with the load (the CPU
hogs evict the caches, the network IRQ thread and the NAND path run at their own priorities)
and whatever the GPIO path does with interrupts disabled. Raising the GPIO bank's IRQ thread to
SCHED_FIFO 90 (above the user thread) changes nothing, so the IRQ thread is not what waits.
Note that today's plain-kernel load capture (max 422 µs) is far below the October one (6L: max
1.45 ms); the October system had other things running (OpenPLC web server, no `performance`
pinning of the IRQ affinity...) and the LA sampled at 200 kHz; the same-day pair is the one to
trust for the kernel comparison.

What this means: for a periodic PLC cycle (timer-driven, the way OpenPLC and any runtime of
our own work) PREEMPT_RT is a clear win: 1 ms cycles with < 100 µs jitter under full load
instead of 350 µs. For reacting to a single input edge from user space the kernel choice
matters less than the design: no flash writes and no network floods during control, or
move the edge handling into the kernel (a small driver) or out of Linux (bare metal, 560 ns).
The fleet kernel can become PREEMPT_RT at no cost in boot time or image size; the cost is
~17 µs on an idle edge response and the external patch to carry with each kernel update.
Decision (2026-11-03): the fleet kernel is PREEMPT_RT (`linux-antminer_6.12.bb`,
`kernel/defconfig`).

**Pitfall found when switching (2026-11-03): a saturating RT task freezes the RT kernel.**
OpenPLC runs its cycle thread at SCHED_FIFO 30. With a 1 ms task (`gpio-echo-1ms.st`, ~1.3 ms of
work per cycle) the thread never sleeps. On the plain kernel softirqs and timers run in interrupt
context, so the board stays usable (load ~5). On PREEMPT_RT the timer softirq runs in the kernel
thread `ktimers/0` at SCHED_FIFO 1, RCU callbacks in `rcuc/0`/`rcub/0` (FIFO 1) and the rest in
`ksoftirqd/0`: all below OpenPLC, so they starve, timers stop firing and the board froze ~95 s
after every boot until the hardware watchdog reset it into the NAND kernel. Raising these four
threads to SCHED_FIFO 40 (above OpenPLC, below the IRQ threads at 50) fixed it: the same program
ran for 5 minutes with load comparable to the plain kernel. `antminer-early` (init, S36) now does
this on every boot when `/sys/kernel/realtime` is 1 (busybox `chrt`). Rule for anything new:
a real-time task that can run back to back must use a priority below 40.

## Summary (2026-10-07)

Same board, same wiring, same stimulus; only the software changes. "x bare metal" is the median
relative to variant 7.

| OpenPLC v3, 1 ms task (2) | 1.97 ms | 2.8 ms | 3 500 |
| Linux, C echo, 1 ms periodic (4) | 507 µs | 999 µs | 900 |
| Linux, C echo, interrupt wake-up, `ondemand` (5) | 128 µs | 284 µs | 230 |
| Linux, C echo, interrupt wake-up, `performance` (5c, 6) | 49 µs | 72-86 µs | 88 |
| Linux, interrupt wake-up under load (5cL, 6L) | ~175 µs | ~1.4 ms | 310 (median) / 1 650 (max) |
| Linux, interrupt wake-up, NAND writes only (5cL-nand) | 213 µs | 325 µs | 380 |
| Linux, interrupt wake-up, CPU + network only (5cL-net) | 77 µs | 817 µs | 140 |
| Linux, C echo, busy poll (3) | 5.0 µs | 9.2 µs | 9 |
| **bare metal, busy poll, 550 MHz (7)** | **560 ns** | **850 ns** | **1** |

What moved the numbers, in order of size: the PLC runtime (OpenPLC cycle ~1.3 ms); the cycle
model itself (a periodic cycle adds a uniform 0..period); the cpufreq governor (~100 µs per
wake-up with `ondemand`); non-preemptible kernel work under load (network softirqs: rare
sub-millisecond spikes, NAND writes: +130 µs on every event); the gpiolib threaded-IRQ path
(~34 µs). What did not move them: CONFIG_PREEMPT (idle or loaded), cpuidle `mpu_gate`.

What this means for the project:

- A module with guaranteed microsecond reaction (fast counters, protections, synchronous tasks)
  is realistic on this A8 with bare metal or an RTOS, with 256 MB RAM and Ethernet available.
- A classic PLC with a 1-10 ms cycle is fine on Linux, but not through OpenPLC v3 as it is
  (1.3 ms per cycle); a lean runtime or an optimised hardware layer would give cycles well under
  100 µs.
- A hybrid "Linux for configuration and network + deterministic core for I/O" has nowhere to
  live on this chip (no PRU, one core): it is either/or, or two controllers.

## Conclusions so far (2026-10-07, all on Linux 6.12)

1. The kernel is not the limit on an idle system: 5 us busy-poll, 15 us timer wake-up, 49 us
   interrupt wake-up (with a fixed CPU frequency). CONFIG_PREEMPT changes none of these.
2. Two settings of the fleet image matter more than any kernel option: cpufreq `performance`/a
   fixed OPP (ondemand costs ~100 us on every wake-up) and keeping `mpu_gate` is fine.
3. OpenPLC v3 costs ~1.3 ms per cycle on this CPU regardless of the task interval; it is the
   floor for anything built on it. Its hardware layer reads 8 ADC channels through sysfs every
   cycle; that is the first thing to optimise if OpenPLC stays.
4. Under load the tail is set by non-preemptible kernel work, not by scheduling: network RX
   softirqs (sub-millisecond spikes at 3000 pkt/s) and NAND writes (+130 us on every event).
   CONFIG_PREEMPT does not help; PREEMPT_RT (threaded softirqs, the external 6.12-rt patches on
   32-bit ARM) is the Linux-side lever left to test. Design-wise: no flash writes during control,
   and rate-limit or isolate network traffic.
5. For hard bounds below ~100 us under load, Linux on this single-core A8 is not enough;
   that is the case for the bare-metal / RTOS track.
6. Bare metal (variant 7): 285-850 ns, uniform over one ~565 ns loop iteration; the fixed part
   (~285 ns) is the input synchroniser plus one GPIO write over the L3/L4 interconnect. That is
   9x below the Linux busy poll, ~90x below the Linux interrupt wake-up and ~3500x below the
   OpenPLC 1 ms cycle, at 550 MHz instead of 1 GHz. The hardware is not the limit; the software
   stack is.
